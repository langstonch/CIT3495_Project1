CIT3495 Project 1: Data Collection and Analytics System

Split of work. Part A: Auth Service + Enter Data app + MySQL. Part B: Analytics + Show Results + MongoDB. Part C: Platform, CI/CD, evidence. Use at least two languages (suggested: Python for Auth and Analytics, Node.js for the two web apps).

Shared contracts (agree on day 1, all three sign off)

ItemProposal
AuthPOST /login {username,password} returns JWT. GET /validate with Authorization: Bearer returns 200 + {user} or 401. Shared signing secret via env var JWT_SECRET.
MySQL table measurementsid INT PK AUTO, user VARCHAR(64), category VARCHAR(64), value DOUBLE, created_at TIMESTAMP
Mongo collection stats{category, min, max, avg, count, updated_at}, one doc per category, upserted
PortsEnter Data 3001, Show Results 3002 (published). Auth 5000, Analytics (no port), MySQL 3306, Mongo 27017 (internal only)
Env var namesMYSQL_HOST/USER/PASSWORD/DB, MONGO_URI, JWT_SECRET, AUTH_URL
Networksfrontend (web apps), backend (internal, no published ports)

Part B: Analytics Service, Show Results app, MongoDB

Deliverables

  1. Analytics Service (Python). Loop or scheduled job (e.g. every 30-60 s): read raw rows from MySQL, compute min, max, avg, count per category, upsert into Mongo stats. Must be idempotent and survive a DB being down (retry with backoff, log, do not crash).
  2. Show Results web app (Node.js). Login page uses the Auth Service; page lists stats from MongoDB. Reject requests without a valid token (call /validate). Escape all output (no XSS).
  3. MongoDB container config and named volume for data (Compose entry provided to Part C).
  4. Dockerfiles for Analytics and Show Results: slim/alpine base, .dockerignore, dependency layer cached before source copy, non-root USER, HEALTHCHECK. Analytics image should be multi-stage if it needs build deps.
  5. Tests: unit tests for the stats calculation (empty set, one row, many rows, bad values) and for the Show Results auth guard (no token, bad token, good token). Wire into npm test / pytest so Part C's CI can run them.
  6. Logging: structured JSON logs (job start, rows read, docs written, errors). Never log passwords, tokens or connection strings.
  7. Report sections: analytics design and data flow, Mongo schema choice, how B's services fail and recover, B's security measures.

Presentation (B's part)

Demo: add data in the Enter Data app, wait for the analytics run, see updated stats. Be ready to defend: why Mongo for results, how the job handles failures, why stats are upserted, how the token is checked.

Part C: Platform, CI/CD, evidence

Deliverables

  1. docker-compose.yml for all services. Only Enter Data and Show Results publish ports. MySQL, Mongo, Auth, Analytics on the internal backend network. Named volumes for MySQL and Mongo. depends_on with condition: service_healthy. restart: unless-stopped. mem_limit/cpus on selected services with a written justification.
  2. Secrets: .env.example committed with placeholders; real .env git-ignored; DB passwords and JWT secret read from env or Docker secrets. Repo scanned to confirm nothing real is committed.
  3. Multi-arch images (linux/amd64 and linux/arm64) built with docker buildx. Record image size and build time before/after one real optimization (e.g. single-stage to multi-stage, alpine/slim base, layer reordering, .dockerignore).
  4. CI/CD pipeline (GitHub Actions or GitLab CI): run all unit tests, build images, scan with Trivy (fail on critical, review high), tag (git SHA + latest/version), push to registry (Docker Hub or GHCR) using repository secrets. Needs one fully green run captured as evidence.
  5. Failure tests (at least two): e.g. stop MySQL, stop Auth. For each, record the command, what the user sees, what the logs say, and how it recovers.
  6. Persistence test: insert data, docker compose rm -sf mysql mongo and recreate, show the data is still there.
  7. Load test (k6, wrk or JMeter): fixed script against login + data entry + results. Report throughput, error rate, CPU and memory (docker stats). Make two justified improvements (e.g. DB connection pooling, index on category, tuned worker count, resource limits), re-run and compare in a table.
  8. Docs: architecture diagram (draw.io or Mermaid), README with clean-environment deploy steps (clone, copy .env.example, docker compose up -d, URLs, default test user), and the technical report assembling the evidence tables from A and B too.
